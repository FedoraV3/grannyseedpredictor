# Granny Legacy — Seed Predictor v1.0
## Reverse-Engineering Conclusion & Technical Reference

**Target:** Granny Legacy v1.8.9 (Unity 2022.3.62f2, IL2CPP, x64)
**Goal:** Given a desired item layout, find a seed that produces it — *inverse* seed search.
**Status:** ✅ **Complete and proven in-game.** 3 independent seeds, 5 runs, **155/155 item placements correct.**

---

# 1. Executive Summary

Granny Legacy ships a built-in, seed-driven item randomizer (`SeedManager`). This project reverse-engineered it to bit-exact precision and built a tool that runs it **backwards**: the user pins items to chosen locations, and a GPU search sweeps the 2^32 seed space for a seed producing that layout.

**What made this tractable:**
1. The randomizer is a discrete, deterministic algorithm over ~87 slots — not physics-based.
2. It uses .NET `System.Random`, which is exactly reproducible.
3. The seed is a plain integer the player can type into an **in-game Seed menu**.

**The decisive engineering decision** was refusing to write GPU code until a CPU reference was proven against the real game. Every later validation depended on having an authoritative reference to diff against.

# 2. The Algorithm

## 2.1 Seeding

```csharp
seed = (PlayerPrefs.GetInt("RandomSeed")==1 && this.RandomizeSeed)
     ? UnityEngine.Random.RandomRangeInt(0, 999999999)   // fallback only
     : PlayerPrefs.GetInt("GameSeed");
this.Seed = seed;

attempt = 0; success = false;
while (attempt < 50 && !success) {
    attempt++;                                      // starts at 1, NOT 0
    rnd = new System.Random(this.Seed + attempt);   // RE-SEEDED EVERY ATTEMPT
    RestoreOriginalStates();
    ... Steps A-F ...
    success = !DetectCircularDependencies() && ValidatePuzzleDependencies();
}
```

> ⚠ **`rnd` is not a continuous stream.** Each retry is an *independent* `Random(Seed + attempt)`. Measured: **8.6% of seeds fail attempt 1**, so their real layout comes from `Random(Seed+2)` or later. Ignoring this silently corrupts ~8% of results.

> ⚠ If `RandomSeed == 1` **and** the scene's `RandomizeSeed` field is true (it is), the game **ignores `GameSeed` entirely**. `RandomSeed` must be `0`.

## 2.2 RNG — .NET `System.Random`, confirmed from disassembly

Classic **Knuth subtractive lagged-Fibonacci** (the legacy/"Net5Compat" path). Not xoshiro — no `Xoshiro`/`CompatPrng`/`Net5Compat` symbols exist anywhere in the binary.

| Property | Value |
|---|---|
| `MSEED` | `161803398` (unique immediate at `0x180468158`) |
| `MBIG` | `2147483647` |
| Seed normalization | `(seed == int.MinValue) ? int.MaxValue : abs(seed)` — the .NET **Core** form |
| State | `int[56] _seedArray`, `_inext = 0`, `_inextp = 21`, 4 warm-up passes |
| `InternalSample` | index advance wraps at 56 via `++x; if (x >= 56) x = 1` — **not** modulo |
| `Sample()` | `InternalSample() * (1.0 / 2147483647)` |
| `Next(max)` | `(int)(Sample() * max)` |
| `Next(min,max)` | `min + (int)(Sample() * range)` for `range <= int.MaxValue` |

Requires **fp64** for bit-exactness — `Sample()` is double arithmetic.

## 2.3 Shuffle — backward Durstenfeld Fisher-Yates

```python
for i in range(len(lst) - 1, 0, -1):
    j = rnd.next_int(i + 1)       # j in [0, i] inclusive
    lst[i], lst[j] = lst[j], lst[i]
```

The alternate "forward, `Next(0,n)`" variant gives completely different output. This detail is load-bearing.

## 2.4 Pipeline — RNG consumption order

| Step | Action | RNG cost |
|---|---|---|
| **A** | Greedy puzzle←item assignment over `orderedPuzzles` (stable `OrderBy(Priority)`); chosen item removed from all other pools | 1 `Next(n)` per puzzle with non-empty pool |
| **B** | Required escape items | 1 `NextDouble()` each; then 1 `Next(n)` or `PlaceItemInFreeArea` |
| **C** | Commit Step-A assignments | **none** |
| **D** | Backfill empty puzzles (tier1 strict → tier2 relaxed) | 0–1 `Next(n)` per puzzle |
| **E** | Mandatory-item spawn areas | **dead in this build** (see §4) |
| **F** | `fillAllFreeSpawns`: `Shuffle(remaining)` then place each | `n-1` + per-item cost |

`PlaceItemInFreeArea(item)` = `Shuffle(eligible areas)` (`n-1` calls) + 1 `Next(freeSpots)`, with an **unshuffled** fallback linear scan if no shuffled area had room.

> ⚠ Priority **7 appears twice** (`DrawerCribRoom`, `CoffinSpiderCellar`). The sort must be **stable**, preserving original `puzzleDefs` order for ties. Python's `sorted()` is stable.

### 2.5.1 Float32 Precision (Critical Bug Fix)

`EscapeItemPuzzleChance` is a C# `float32` (`0.7` nominally), but IL2CPP promotes it to `double` as `0.699999988079071`. The JSON dumps store `0.7`. Reading as Python `float` (double) produces `0.7` exactly, which is very slightly too large and would flip the `NextDouble() < chance` comparison for rolls in the interval `[0.699999988079071, 0.7)`, silently corrupting escape-item placement. **Rate (derived, not hand-waved):** `Sample()` yields `k/2147483647`, and exactly **25** integer values of `k` fall in that interval, so the comparison diverges with probability `25/2147483647 = 1.16e-8` per `NextDouble()` roll. Step B makes one roll per required escape item, so the per-seed rate is variant-dependent: **~1.63e-7 (0.0000163%, ~700 seeds of 2^32) for Normal** (14 escape items), ~2.10e-7 for `More` (18), ~4.66e-8 for v1.0 (4). Small, but not zero over a full sweep. The fix (`_as_float32()` in `simulator.py`) round-trips via C `struct` to recover the exact binary representation and is applied in `load_config()`. Variant loading via `variants.py` applies the same correction automatically.

## 2.5 Predicates (disassembly-verified)

- **`IsItemAllowedForPuzzle`** — empty `allowedItemNames` ⇒ **allow-all** (falls through to the exclude check); non-empty ⇒ allowlist-only. `excludeItemNames` applies **only** when the allowlist is empty. **Never reads `requiredItemNames`.** Matching is on `ItemSeedData.itemName`, `.Trim()` both sides, **`OrdinalIgnoreCase`**.
- **`category != 4`** — `ItemSeedData.category` at offset `0x28` (`cmp dword ptr [rax+28h], 4`). Category 4 = "free" items, excluded from puzzle pools. The developer's own tooltip survives in `dump.cs`: `"1=escape-only, 2=escape+puzzle, 3=puzzle-only, 3=free"` (their typo for `4=free`).
- **`IsSafeContainerPlacement`** — a container item is unsafe for a puzzle iff the item's `containedItems` overlaps that puzzle's `requiredItemNames`. Uses **plain case-sensitive, no-Trim** comparison — deliberately different from the above.
- **No hash-order dependence.** Every RNG-relevant sequence runs over `List<T>`/arrays via `.Where().ToList()`. Python `dict`/`set` are safe; .NET bucket ordering never needs replicating.

## 2.6 Quirks reproduced faithfully (do NOT "fix")

- Step E marks a mandatory item as used **even when placement silently no-ops**.
- If all 50 attempts fail, the **last invalid layout stands**.
- Total `maxItems` across areas is **20** but there are **31 items** — not every item can reach a free area. Real behavior, not a bug.

# 3. Seed Lifecycle & Injection — *the biggest practical gotcha*

Only a handful of functions in the entire binary touch the seed PlayerPrefs keys:

| Function | VA | Role |
|---|---|---|
| `SeedManager.GeneratePlacement` | `0x18024F770` | **reads only** |
| `Menu_Seed.Start` | `0x180249EB0` | reads both to populate the **in-game seed UI** |
| `Menu_Seed.Update` | `0x180249FA0` | writes `RandomSeed` every frame the menu is open; writes `GameSeed` + `Save()` on Enter/Escape |
| `Menu_Seed.ExitTypingModeAndSave` | `0x180249E00` | writes+saves `GameSeed`; **no static caller** — fired by Unity UI events, can re-commit *stale* text |
| `MainMenu.Start` | `0x180221541` | one-time `CURVERSION`-gated migration that force-sets `RandomSeed = 1` |

## ✅ The working method: the in-game Seed menu

**The game ships a seed input.** Type the seed, press Enter, start a run. **Empirically confirmed.**

## ❌ What does NOT work: writing the registry

`HKCU\Software\Omega Mega Gigal Intel\Granny: Legacy\GameSeed_h510350364` (REG_DWORD, note the **colon** in the product name).

Writing it **did not reach the game**, tested on a clean launch *after* the write. The seed menu still displayed the old value. Nothing in the game auto-overwrites `GameSeed`, so the cause is most likely Unity's in-memory PlayerPrefs cache combined with `Menu_Seed` re-committing stale field text. **Exact mechanism UNCONFIRMED.**

> **Conclusion: the in-game Seed menu is the supported path.** `seed_registry.py` exists and is correct, but ships as experimental and must not be the primary mechanism.
> Also note: Unity rewrites *all* PlayerPrefs from memory on exit, so any external write while the game is running is guaranteed to be clobbered.

The scene holds **10 inactive `SeedManager` instances** (GameObjects `SeedSystemManager_1.0`…`_1.7`, `_Normal`, `_More`) under `GameManager/HandleObjects`; one is activated at runtime based on the player's selection.

> ❗ These are **GameObject names, not classes.** However, **`VersionControl` and `VersionControlItemChange` classes *do* exist** (`VersionControl$$Start` @ `0x180214fd0`, `VersionControlItemChange$$Start` @ `0x18022c620`). **`CURVERSION` is actively read** — 10 times in `VersionControl$$Start` and 3 times in `VersionControlItemChange$$Start`. It is **not** a migration flag.

### Variant Selection

**The variant selector is `ObjectsManager.Start()`** (RVA `0x22E7B0`, on `GameManager/HandleObjects`). Its Inspector fields are named `Seed_Main` / `Seed_Extra` / `Seed_17`…`Seed_10` — the string "SeedSystemManager" does not appear in the binary, which is why prior searches missed it.

```
if (PlayerPrefs.GetInt("FlashL") != 1)       -> no seed system; old fixed preset layout
else if (PlayerPrefs.GetInt("Extras") != 0)  -> _More
```

All 10 variant GameObjects have `m_IsActive == false` in the serialized scene; `ObjectsManager.Start()` activates exactly one.

# 5. Feasibility — variant-dependent

Expected matching seeds over the full 2^32 space ≈ `2^32 / N^k` for *k* pinned items, where *N* is the variant's total addressable slots.

### Normal variant (87 slots)

| Pins | Expected seeds | Verdict |
|---|---|---|
| 1 | ~60,000,000 | trivial |
| 2 | ~852,000 | trivial |
| 3 | ~12,000 | fine |
| 4 | ~169 | **borderline** |
| 5 | ~2.4 | coin flip — may not exist |
| 6+ | ~0.03 | **effectively impossible** |

**~4 pins is the reliable ceiling for Normal.** This is information theory, not an implementation limit — no amount of optimization changes it. It is also precisely why a full-space GPU sweep is *necessary*: at 4–5 pins you must scan everything to find the handful of solutions.

### Earlier variants — more favorable

Smaller variants allow more pins due to their smaller denominators:

| Variant | Slots | ~5 pins | ~6 pins | ~7 pins |
|---|---|---|---|---|
| 1.0 | 39 | ~1,857 expected | ~48 | ~1.2 |
| 1.1 | 49 | ~306 | ~6.2 | ~0.1 |
| 1.2 | 51 | ~257 | ~5.0 | ~0.1 |
| 1.3 | 58 | ~158 | ~2.7 | ~0.05 |
| 1.4 | 67 | ~90 | ~1.3 | ~0.02 |
| 1.5 | 71 | ~71 | ~1.0 | ~0.01 |
| 1.6 | 72 | ~67 | ~0.93 | ~0.01 |
| 1.7 | 79 | ~51 | ~0.65 | ~0.008 |
| Normal | 87 | ~2.4 | ~0.03 | ~0.0003 |
| More | 89 | ~2.0 | ~0.022 | ~0.0002 |

**v1.0 reliably supports ~5–6 pins** vs ~4 on Normal.

# 6. Tool Architecture

```
gui.py              Tkinter UI — pin / prefer / don't-care, live feasibility, GPU auto-select
  └── search.py         Constraint, SeedResult, SearchBackend protocol, CpuSearchBackend
        ├── gpu_backend.py + kernel.cl    OpenCL, ~6.05M seeds/sec
        └── simulator.py                  authoritative reference
              └── net_random.py           bit-exact System.Random
ground_truth.py     joins mod dumps -> {item: slot}; the acceptance test
validate_all.py     regression suite over every captured dump
seed_registry.py    registry read/write + auto-backup  (EXPERIMENTAL)
mod/ + SeedDumper.dll   MelonLoader mod: dumps live config + actual placements
```

**Design principle — GPU filters, CPU adjudicates.** The kernel evaluates seeds; every candidate is re-verified with `simulator.py` before being reported. Zero false positives by construction.

**No strings on the GPU.** The host compiles all predicates into 32-bit bitmasks over the 31 item indices, so the kernel is pure integer/double work with no dynamic allocation.

**fp64 is required and checked** — the backend fails loudly rather than degrading to float, which would silently produce wrong seeds.

## Performance

| Backend | Throughput | Full 2^32 sweep |
|---|---|---|
| GPU (RX 7700 XT, gfx1101, 27 CU) | **6,051,063 seeds/sec** | **~12 minutes** |
| CPU, 1 core | ~164 seeds/sec | impractical |

> The "36,986x" single-core figure is **measured**; the "~2,300x vs 16 cores" figure is an **estimate** assuming linear scaling. Don't quote the latter as measured.

## ⚠ Early rejection: the subtle trap

Aborting a seed as soon as a pinned item mismatches is **silently wrong** — measured **18/20,000 seeds (0.09%) mispredicted**, because a naive abort cannot know whether the attempt it is inspecting is the one the game keeps.

**Provably-safe replacement:** an attempt is accepted iff **no container item has landed on a puzzle spawn by the end of Step D**. Puzzle assignment happens only in Steps A–D, so this is decidable before Steps E/F run. Early-abort is enabled only once acceptance is proven this way.

# 9. Known Limitations

1. **~4 pins maximum for Normal variant** (§5). Information-theoretic, not fixable. **Smaller variants support more pins** (e.g. v1.0 supports ~5–6 pins).
2. **No end-to-end in-game confirmation for non-Normal variants.** The existing 155/155 in-game ledger is all `Normal` seeds. Version-specific prediction is validated against the CPU simulator, GPU kernel, and the live mod dump for `Normal`, but no seed from v1.0, v1.1, etc. has yet been played end-to-end and verified in-game.
3. **Spot labels are opaque.** `Area/Spot (29)` — the area is meaningful, the index is not. *This is the top usability gap.* Cheapest fix: a keybind in `SeedDumper` that logs the nearest spot label to the player's position, so spots can be mapped by walking around once.
4. ~~**Cancel latency** up to ~13s worst case~~ — **FIXED in v1.0.1**, see §12. Cancel is now effectively instant.
5. **A `limit` of 0 is rejected** by the GUI. A non-positive limit is falsy downstream and disables the search's internal break conditions, which reinstates the v1.0.0 hang.
6. **`CpuSearchBackend` "quick scan" default** (`0..100,000,000`) is not quick on CPU — hours. Only matters if no GPU is present.
7. **Scene-config dependent.** A game update or an update to the house version's item/puzzle/area set needs a fresh `SeedDumper` dump.
8. **Unverified inferences** (documented, unexercised by tested seeds): Trim/OrdinalIgnoreCase extended by consistency to `usedItemNames`/`itemsByName`/`requiredEscapeItemNames`; `GetEffectivePuzzleOfItem`'s fallback for an item not yet placed in the current attempt.

# 11. How to Use — Version-Control Seeds

```
python gui.py
```

1. **Select the House version** from the dropdown (default `Normal`). The GUI shows live feasibility and expected pin ceiling for the chosen variant.
2. Pin the items you care about. The ceiling depends on the version — smaller variants support more pins (e.g. v1.0 allows ~5–6 vs ~4 on Normal; see §5).

4. Copy the resulting seed.

# 12. v1.0.1 — Post-release bug fix

**Symptom:** with a single pinned item, clicking Search hung on "Starting search...", GPU utilisation stayed near zero, and Cancel stuck on "Cancelling...".

**Root cause — CPU verification, not the GPU.** `GpuSearchBackend.search()` re-verifies every GPU candidate with `simulator.simulate()` (~164 seeds/sec, ~40,000x slower than the dispatch that produced them). Three compounding defects:

1. The verification loop had **no `limit` check** — it verified every candidate in the batch even after enough results were collected.
2. It had **no `cancel_evt` check** — cancellation was only tested between GPU dispatches, so Cancel could not interrupt it.
3. The batch-size adapter scaled on **GPU dispatch time only**. The GPU finishes in milliseconds, so the batch grew toward the maximum — precisely when CPU verification was the bottleneck.

With one pin the hit rate is ~1/71, so a multi-million-seed batch produced hundreds of thousands of candidates, each verified serially: tens of minutes of pure CPU with an idle GPU and a dead Cancel button. Tighter constraint sets masked the bug because their hit rates are orders of magnitude lower.

**Fix:**
- The verification loop now honours `limit`, polls `cancel_evt` every 16 candidates, and reports progress every 64.
- Batch adaptation now uses **total elapsed time** (dispatch + verification) instead of dispatch time alone. This is also strictly safer for Windows TDR, since total time is always >= dispatch time.
- `gui.py` rejects a limit below 1.

**Measured result (the user's exact case: 1 pin, full 2^32 range):**

| | Before | After |
|---|---|---|
| Time to first results | hung indefinitely | **0.1s** |
| Cancel latency | never completed | **instant** |

Regressions re-run and still passing: GPU bit-exactness **6009/6009** (incl. all 345 retry-required seeds), seed `915074960` found, seed `10408711` found, throughput 6.01M seeds/sec.

**Lesson:** in a hybrid GPU/CPU design, the *verification* stage silently becomes the bottleneck as constraints loosen — the opposite of the intuition that looser constraints are cheaper. Any long-running inner loop needs its own cancellation and limit checks; guarding only the outer loop is not enough.

# 13. Launcher

| File | Purpose |
|---|---|
| `run.bat` | Starts the GUI with `pythonw.exe` (no console) and self-closes. Normal use. |
| `run_debug.bat` | Runs with `python` + visible console. Use if `run.bat` appears to do nothing. |

## ⚠ `pythonw.exe` sets `sys.stderr` to `None`

With no console attached, `sys.stdout`/`sys.stderr` are `None`. PyOpenCL warns while building the kernel, the warnings machinery writes to `sys.stderr`, and the process **dies before the window appears with no visible error**.

`gui.py` guards against this at the top of the module (right after the `__future__` import), redirecting missing streams to `logs/gui.log` and falling back to `os.devnull`. Any GUI-launch problem should be diagnosed from that log, or by running `run_debug.bat`.

> Note: `ast.parse()` does **not** enforce that `from __future__` must be the first statement — only `compile()` does. A file can pass an `ast.parse` check and still be unimportable.
